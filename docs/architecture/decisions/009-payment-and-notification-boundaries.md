# Sandbox payments and transactional notifications

**Status:** Accepted for the current test-mode integration

**Context:** Checkout must keep server-authoritative prices, promotions, stock reservation, and idempotency. ShopSmart must not process card data, trust a browser return as proof of payment, or let an email vendor outage change a committed commerce outcome.

**Decision:** Checkout creates one pending-payment order and one normalized payment record, then returns a Stripe-hosted Checkout URL only when Stripe test credentials are configured. The provider adapter owns Stripe-specific requests, signature parsing, and status normalization. A signed, time-bounded webhook must explicitly be marked `livemode=false` and match the persisted session, order, INR amount, and status before one transaction changes payment/order state. Webhook IDs and provider idempotency keys make retries safe. Failed attempts reuse the owner-scoped order/payment with a bounded retry count; the checkout idempotency key persists for an unchanged cart across refresh. Test/live key separation is enforced in configuration and the adapter.

The same verified payment transaction queues semantic email intents in a unique notification outbox. A separate private worker renders responsive HTML/plain text and dispatches through an `EmailProvider`. Queueing does not commit the caller's transaction; delivery retries use leases and a finite backoff budget. Sent and terminally failed rows retain only their dedupe/audit stub; recipient and message payload are redacted. Local/test console and capture providers are the only shipped adapters. External email providers fail closed until a real adapter is implemented and reviewed.

**Consequences:** Missing Stripe sandbox configuration or invalid return URLs disable checkout with a safe error before inventory is reserved, while catalog and account browsing remain available. Hosted Checkout totals are checked against Stripe's INR bounds before order creation. Payment return URLs only help the customer find their order; the owner-scoped order API reports verified status. Ambiguous session-creation failures keep the reservation retryable under the same provider idempotency key. Stripe sessions expire after two hours; a three-hour in-process sweeper restores stock for pending orders without a saved provider session. Definitive provider rejection cancels the order and restores stock transactionally. A failed payment remains retryable with stock reserved until the bounded retry budget is exhausted; the final verified failure closes the order and restores inventory. Cancelled orders clear the saved checkout idempotency key so a new order can be created. A verified Checkout expiration also cancels the order and restores the reserved quantities transactionally. Successful payment consumes only matching ordered quantities from the shopper cart. Commerce audit events use the existing structured logging pipeline under `shopsmart.commerce.audit`; deployment log aggregation/retention is the audit record, while the webhook table is only a dedupe marker. Notifications are at-least-once: a process crash after provider acceptance can cause a duplicate, which is documented for future provider idempotency support. The outbox stores destination and minimal order content only while delivery is pending/retrying.
